MethodIntel: what the plan misses, and what to do about it

A gap analysis of the three planning docs (plan · router_todo · artifacts), plus a re-ordered Phase 1 that validates the thing actually worth building — the graph — instead of validating a single isolated card.

Scope: Phase 0–1 + schema Verdict: Build it — but re-sequence Redundancy vs Deep Research: Settled / non-issue

The short version

The plan has already won the argument you opened with: LitIntel is paper-centered, MethodIntel is decision-centered, and the four-axis decision model — method × implementation × ecosystem × validation burden, kept separable — is the single best idea in the document. That is exactly what Deep Research and the architecture skill both flatten. Stop relitigating redundancy.

The problem is sequencing, not concept. The graph is the only reason this isn't redundant, and the plan defers the graph to Phase 4.5 while shipping a flat card in Phase 1. You are about to validate the tiling before checking whether the tunnels connect.

01

What you miss

// eight gaps, ranked by how much they bite. four are from the live critique; four surfaced on full read.
Critical
GAP-01 · sequencingThe graph is deferred — but the graph is the whole moat
Problem

Phase 1 ships a flat MethodDecisionDossier with a single MethodGraphEdge stub; the node taxonomy (StageNode, sensitive_to, contradicted_by) is pushed to Phase 4.5 "after one dossier validates Phase 1."

Why it bites

A single dossier has no edges to other dossiers. Graph value only appears at N≥2. Your Phase 4 review literally asks "does the schema capture graph edges?" — a question one isolated dossier cannot answer.

AnalogyYou're tiling the first subway station and checking the signage before deciding where any tunnel connects. The station looks finished; you've learned nothing about the network.
Fix

Make the MVP two connected dossiers (Stage 4 integration + Stage 5 clustering) sharing one sensitive_to edge — the LSI/embedding choice upstream of every clustering claim. One dossier tests the card; two tests the graph.

Critical
GAP-02 · missing operation"Consequence synthesis" — the 60–70% you flagged yourself — vanished
Problem

Your own scheme doc named step 4 the crown jewel: "if I use this method here, what downstream claims become stronger, weaker, circular, incompatible?" The plan schema-fies the storage of consequences (edges, trade-off dims) but never specifies the operation that computes them.

Why it bites

This is the difference between a tool that annotates "Leiden is sensitive to embedding" and one that says "you chose LSI in Stage 4, therefore your Stage 7 co-accessibility claim is circular." Only the second is worth your engineering hours. The plan builds the database and forgets the query.

Fix

Promote consequence-propagation to a named Phase 1 operation, even crude: given option set + pipeline edges, emit the list of downstream claims affected by each upstream choice. This is graph traversal, not an LLM call — cheap, deterministic, auditable.

High
GAP-03 · your own principleNo evaluation harness — no definition of a "correct" dossier
Problem

Phase 4 is "compare generated output against the current Notion page" — a one-time manual eyeball. There is no golden set, no agreement metric, no false-recommendation check. Your LitIntel refactor explicitly has an eval harness with tier agreement + false-positive metrics. MethodIntel has none.

Why it bites

Without a harness you can't tell a schema regression from a model-quality regression when you expand to Stage 4, 6, 7. You'll be flying on vibes — the exact failure your "subjective signals are valid alongside metrics" principle warns against. Vibes are a supplement, not the instrument.

Fix

Define 2–3 golden dossiers with hand-graded recommendations + evidence sets. Metric: does the LLM build reproduce the human recommendation, and does every claim resolve to a real source? Run it on every schema change.

High
GAP-04 · false assuranceThe verifier only checks PMIDs — so "verified" will quietly lie
Problem

verify_evidence_claims() resolves PMID refs and marks everything else (docs, github, personal_obs) as verified=None. But your most decision-relevant, fastest-drifting claims — "ArchR addClusters() defaults to Louvain," "SnapATAC2 scales to N cells" — are exactly the docs/github ones.

Why it bites

A reviewer skims a wall of green PMIDs and trusts the whole artifact. This is the "beautiful graph that encodes wrong assumptions" failure arriving through the verification layer instead of synthesis.

Fix

Rename so None reads as "unverifiable-by-system — human must check," and have the Markdown renderer surface those claims in the same follow-up block as verified=False. Never let "no verifier exists" render as visual parity with "verified true."

High
GAP-05 · router bloatstaleness_check is a cathedral for a post-it problem
Problem

A whole fifth router mode + its own lifecycle-report artifact + a deferred six-tier enum, all aimed at one job: "is Cufflinks outdated." Be honest — this is a guard against your own training-era defaults. Real risk, wrong size.

Why it bites

This is the skill-routing-precision failure you've correctly resisted everywhere else. Every extra mode dilutes router classification accuracy. You're paying for a fifth lane to carry one bicycle.

Fix

Demote staleness to a field on every dossier (last_reviewed + a "flag if >18mo" rule), not a mode. Keep four router modes. The signal is right; the surface area is wrong.

Medium
GAP-06 · judgment captureNo structured slot for the human overriding the recommendation
Problem

lifecycle_status is user-confirmed, but the recommendation isn't. When you disagree with the LLM's Stage 5 call, there's nowhere in the persisted JSON to record your override + rationale. It gets lost in a chat or a Notion edit.

Why it bites

This is precisely the authorship-vs-approval distinction you live by. A dossier that only stores the machine's recommendation makes you an approver. Capturing your override + reasoning makes you the author — and builds the heuristic library that is MethodIntel's long-term value.

Fix

Add human_decision + human_rationale + agreed_with_llm: bool to the dossier. Over time, the disagreements become your most valuable HeuristicNode seeds.

Medium
GAP-07 · reproducibilityThe output dossier isn't provenance-stamped
Problem

Options carry a version field, but the dossier output doesn't stamp which LLM model, which prompt version, which retrieval date, or which package versions produced it. Reproducibility is #2 in your own code-review priority order — it shouldn't be missing from the artifact that is the deliverable.

Why it bites

Six months out, a dossier recommends Leiden and you can't tell whether that was Gemini Pro reasoning over 2024 benchmarks or 2026 ones. An un-stamped decision artifact is a rumor with a schema.

Fix

Add a provenance block: model, prompt_version, build_date, source_coverage, pkg_versions. One block, written once at build time.

Medium
GAP-08 · the decisive oneEdges have no review cadence — so the graph rots silently
Problem

last_reviewed exists on lifecycle status but there's no equivalent on sensitive_to / replaces_or_modernizes edges. Nobody owns re-checking whether an edge is still true.

Why it bites

A decision graph whose edges aren't re-reviewed rots faster than prose — because it looks authoritative while going stale. This is the one question that decides whether MethodIntel becomes a career asset or a beautiful dead repo.

Fix

Put last_reviewed + reviewer on every edge. Add a CLI command that lists edges older than a threshold. Edge maintenance is the product.

The one question that decides everything

Who maintains the edges, and how often?

Everything above is tractable engineering. This isn't — it's a discipline question, and it's the one your own scheme doc already identified as the failure mode: a beautiful graph that encodes wrong assumptions.

A method-decision graph whose sensitive_to and replaces_or_modernizes edges aren't re-reviewed decays faster than a prose note — because it carries the visual authority of structure while quietly going false. Close GAP-08 before you write schema.py, or the rest is scaffolding for a repo that ages into a liability.
